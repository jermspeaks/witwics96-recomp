## Project baseline

- **Observed (project brief):** The project owner wants a playable macOS port of *Where in the World Is Carmen Sandiego?*, described as a 1990s Windows game.
- **Observed (repository):** At initial setup, the repository contained a one-line `README.md` and a local `input/` directory; no `.gitignore` was present. Git reported the root `.DS_Store` and `input/` as untracked before this setup.
- **Observed (filesystem inventory, 2026-10-12):** `input/` occupied approximately 635 MB according to `du -sh` and contained 432 regular files. The inventory included the directories `AUTORUN`, `E_REG`, `MOVIES`, `SETUP16`, `SETUP32`, `UTILS`, `WORLD16`, and `WORLDNET`.
- **Observed (filename/extension inventory only):** The tree contains 218 `.MOV`-named files, 15 `.MHK`-named files, and 19 `.EXE`-named files, as well as setup, library, font, configuration, and other files. These counts describe names only; no formats, contents, code, or behavior were analyzed.
- **Observed (repository policy):** The owner requires a bring-your-own legally obtained copy. The local `input/` directory must stay out of Git, as must the game, extracted proprietary assets, and other copyrighted payloads.
- **Inferred:** The directory names and extensions look consistent with Windows installation/media data, but this has not been validated. Do not use this as a compatibility or format claim.
- **Unknown:** The exact release/version, authenticity, executable architecture, file-format details, runtime dependencies, licensing/redistribution rights, and whether any original component runs on current macOS have not been established.
- **Unknown:** The intended technical approach (native reimplementation, compatibility layer, or another architecture), minimum macOS version, and acceptable local asset workflow have not been decided.

## Phase 1 — static artifact reconnaissance (in progress)

- **Observed (supplied documentation):** `input/README.TXT` identifies itself as a read-me for *Where in the World Is Carmen Sandiego?* v3.0 and is dated 1996-04-24. It documents Windows 3.1 and Windows 95 variants, references QuickTime 2.1 for digital video/opening animation, and discusses 256-color and 16-bit-color modes. These are claims in a supplied read-me, not independent authentication of the copy or proof of runtime behavior.
- **Observed (supplied setup metadata):** `input/AUTORUN.INF` declares autorun, installation, registration, and read-me commands, including separate `SETUP16` and `SETUP32` installer entries. `input/SETUP.CFG` selects `setup32\setup32.exe setup32` for the 32-bit setup and `setup16\setup16.exe` for the 16-bit setup. `input/SETUP16/CARMEN.INF` maps source `CARMEN` to installed `carmen.exe` at 558,608 bytes; `input/SETUP16/CARMEN.BDF` maps the `CARMEN` file entry to `carmen.exe` and declares product version 3.0. `input/SETUP16/CARMEN` matches the declared size.
- **Observed (32-bit installer declaration):** `input/SETUP32/SETUP32.INI` labels the product version 3.0, names the installed executable `Carmen32.exe`, sets its start-menu command, and declares `input/SETUP32/ARCHIVE/ARCHIVE.C2K` as the transfer source. It labels the separate QuickTime for Windows installer as required. These are installer declarations; the archive was not unpacked and the executable was not independently observed.
- **Observed (16-bit runtime declarations and executable strings):** `input/SETUP16/CARMEN.INF` and `input/SETUP16/CARMEN.BDF` declare QuickTime 2.1.0 / required QuickTime installation. Read-only `strings -a input/SETUP16/CARMEN` finds the embedded message “This program requires QuickTime version 2.1 or higher” and filename strings for `C2K.MHK`, `Country.MHK`, `Dialog.MHK`, `Guides.MHK`, `Chr1.MHK`–`Chr8.MHK`, `Arrest1.MHK`, `Database.MHK`, and `SYSTEM.MHK`. These static strings support candidate dependency/resource names, not proof that every named file is opened on every run. A filename search found no loose `SYSTEM.MHK` under `input/`; its role or location is unknown.
- **Observed (loose executable inventory):** A `find`/`file` scan classified 19 loose `.EXE`-named files. Five are PE32 x86 executables: the autorun program, registration program, QuickTime 32-bit installer, `input/UTILS/ICOMP.EXE`, and `input/WORLDNET/DISK1/UNINST.EXE`. No loose `Carmen32.exe` was found. This does not rule out an executable stored inside `ARCHIVE.C2K`.
- **Observed (file identity):** `input/SETUP16/CARMEN` is 558,608 bytes, and the host `file` utility identifies it as an MS-DOS NE executable for Windows 3.x. Its SHA-256 is `246b63519dd84f1fac070045972c759dd4c38bc5110d6c74106f7903ff49f83e`.
- **Inferred (bounded):** The matching setup entry, file name, and declared size make `input/SETUP16/CARMEN` a strong candidate for the Windows 3.1 game executable. The setup table is declarative; installation was not performed and no execution was observed.
- **Observed (data type survey):** A focused `file` scan classified the 218 `.MOV`-named files as 211 fast-start and 7 unoptimized Apple QuickTime movies. A first-four-byte check of all 15 `.MHK` files found `MHWK` in every file; the representative `input/DATABASE.MHK` also has the bytes `RSRC` at offset 8. `file` reports these as generic `data`. **Inferred:** the marker bytes are consistent with a Mohawk resource container, but no parser validated the format, internal structure, or resource contents. `input/DATABASE.MHK` is 3,142,974 bytes, SHA-256 `be12b3f29342723fe7c900643ea362e50fb78beb52a5c8234f5326bf40a7255d`. The 218 movie classifications and the five InstallShield Z classifications remain signature-based, not proof of runtime use.
- **Observed (manual NE header/table survey, 2026-10-12):** A bounds-checked, read-only Python standard-library parse of `input/SETUP16/CARMEN` found an `MZ` header pointing to an `NE` header at file offset 592. The NE header declares 29 segment records and an alignment shift of 9; every nonzero segment range computed from the segment table was within the 558,608-byte file. The module-reference table resolves to five imported-name strings: `GDI`, `KERNEL`, `MMSYSTEM`, `USER`, and `WIN87EM`. This is declared import-table metadata, not proof that all modules are used at runtime or a complete dependency inventory; dynamic lookups and behavior are not covered. The analysis was limited to header/segment/import table fields; instructions were not decoded.
- **Observed (analysis tooling, bounded checks):** REA package 6.4.0 is connected. Ghidra 12.1.4 is available on macOS arm64; Hopper is unavailable at `/Applications/Hopper Disassembler.app/Contents/MacOS/hopper`. `open_binary` rejected both `input/SETUP.EXE` and `input/SETUP16/CARMEN` as unsupported NE executables. Apple LLVM `objdump` 21.0.0 also rejected `input/SETUP16/CARMEN` as not a valid object file; `llvm-readobj` could not be found through `xcrun`. The checked command set did not include `unshield`, `innoextract`, `unar`, `scummvm`, `winedump`, `radare2`, or `rizin`; checked Python modules `pefile`, `lief`, `construct`, `macholib`, `capstone`, and several archive/parser modules were absent. `/Applications/The Unarchiver.app` is present (bundle version 4.3.9, build 147); its inspected `Contents/MacOS` directory contains only the GUI executable, and its `Info.plist` does not declare `.C2K` or `.MHK` as document types. No `unar` command was found on `PATH`. These bounded checks did not identify a usable NE analyzer, Mohawk reader, or InstallShield Z extractor; they are not an exhaustive software inventory. No instruction decompilation or REA Evidence record was produced for the NE targets. The installed skill file is version 40 while the live server reports expected skill version 37; the actual tool inventory and schemas were used.
- **Observed (archive/tool follow-up, 2026-10-12):** `file input/SETUP32/ARCHIVE/ARCHIVE.C2K` reports “InstallShield Z archive Data”; `bsdtar -tf input/SETUP32/ARCHIVE/ARCHIVE.C2K` fails with “Unrecognized archive format,” so it did not enumerate archive members. The archive SHA-256 remains `fe6210cd08cf6a3d4a2e163e0ff41414a12f1419a6288ee80f39a65ddf300653`. The Unarchiver app’s declared document types include CAB, MSI, and a generic archive handler, but not `.C2K`; it was not launched against the archive and no extraction was attempted.
- **Observed (NE support follow-up, 2026-10-12):** Hopper’s official FAQ says it reads Mach-O, PE32/PE32+/64 Windows, and ELF binaries; it does not document NE support. The FAQ’s listed processor support (Intel 32/64-bit, ARM, PowerPC) does not establish support for this NE image or its 16-bit execution model. The local Ghidra route already rejected the NE file. External references: [Hopper FAQ](https://www.hopperapp.com/faq.html), checked 2026-10-12; [OSDev NE format reference](https://wiki.osdev.org/NE), checked 2026-10-12, which describes NE as the separate 16-bit format; [win16ne parser project](https://github.com/qnighy/win16ne), checked 2026-10-12, an example of a dedicated NE parser/disassembler rather than evidence of a locally installed tool.
- **Observed (repository safety):** `git check-ignore -v input` confirms the root `/input/` ignore rule; `git ls-files -- input` returned no tracked paths. The inspections were read-only: no game file was extracted, modified, or executed.
- **Unknown:** The bytes and format of the declared `Carmen32.exe` inside the InstallShield archive, the complete mapping of archive contents to installed files, the detailed `.MHK` format/resource index, the complete runtime dependency set beyond the five module-reference names, and the game's runtime behavior remain unresolved. No build or tests exist/run for a port at this stage.
